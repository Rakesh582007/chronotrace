# Decision log

Each entry records what was decided and why, so anyone on the team can answer a judge's "why did you do it this way?"

| # | Decision | Why |
| --- | --- | --- |
| 1 | Any chronic condition, tagged per patient (replaces the oncology-only ONCOTRACK pitch) | Cancer response is judged on imaging (RECIST), which a lab-report pipeline cannot read |
| 2 | Flag change from the patient's own baseline; printed reference range is context only | Chronic patients are always out of range, so range-based flags become noise |
| 3 | A change counts only if it exceeds the reference change value (e.g. ~14% for creatinine) | Smaller changes are within normal lab and biological variation |
| 4 | Trained model is used for extraction only (DistilBERT, row-level NER) | Learning helps with messy report layouts; clinical judgement needs verifiable rules |
| 5 | Training data is generated synthetically with automatic labels; real reports are the test set only | Synthetic data is valid for learning layouts, and a real-report test set keeps the accuracy number honest |
| 6 | Trend math is done in code; the LLM only summarises computed flags | LLMs are unreliable at reasoning over long patient histories |
| 7 | "Drug effectiveness per body type" dropped; replaced by "response after medication change" with no score | Regression to the mean, unknown adherence and confounding by indication make a score misleading; "body type" is not a validated drug-response variable |
| 8 | Stack: FastAPI, SQLite, React + Vite + Recharts, pdfplumber/EasyOCR, pandas/scipy, hosted LLM | Fits a 24-hour build on one RTX 3050 laptop, with an 8 GB laptop as backup demo machine |
| 9 | Patient age for eGFR is report year minus birth year (`Patient` stores only `birth_year`) | Asking for a full birth date adds friction and identifying data. The age can be up to 1 year too high before the birthday; at 0.9938 per year in CKD-EPI 2021 that moves eGFR by about 0.6%, well inside its 20% change threshold (KDIGO 2024 PP 2.1.3) |
| 10 | Trends and flags are computed on every request, not stored | They can never go stale after an edit, a newly confirmed report or a deleted medication; the whole history of one patient is small |
| 11 | The slope skips results up to the end of the last expected-effect window of a drug that affects the analyte | The planned eGFR dip after starting an ACEi/ARB or SGLT2 inhibitor would otherwise read as progression (demo patient: naive slope -9.8/yr, true post-start slope -7.1/yr) |
| 12 | Known limit: expected drug effects (and their windows) apply to drug **starts** only | The KDIGO 30% creatinine rule also covers ACEi/ARB dose increases; a `dose_change` event does not get an expected-effect note yet |
| 13 | Changes between two different labs are labelled `cross_lab`, not re-thresholded | The RCV only covers within-subject and analytical variation in one lab; between-lab differences are larger, so such changes carry a note until a between-lab RCV is sourced |
| 14 | A medication's "before" value is the mean of the last 2-3 results (within 180 days, after any earlier drug affecting the same value) | A single value picked before a treatment start is often a high one; averaging dampens regression to the mean. Every start-event response also says that some change is expected from regression to the mean and that adherence is not recorded |
| 15 | eGFR's change threshold is KDIGO's 20% (Practice Point 2.1.3), not an RCV derived from creatinine | A published, verified threshold for people with CKD beats an unverified propagated one (15.4%); the RCV of every other analyte still comes from biological variation |
| 16 | Demo login: one seeded doctor, stdlib signed token | Not production auth: no rate limiting, no refresh, no password reset. The doctor comes from .env (the app refuses to start without it); tokens are HMAC-SHA256 over doctor id and expiry (12 h); data is scoped per doctor and another doctor's data answers 404 |
| 17 | LLM summaries: the model sees only engine facts, and code checks every answer before it is saved | Facts are the patient's code, sex, age and recorded conditions, report labels, flags, trends, medication responses and computed data notes; never the name, a PDF or report text. An answer is rejected if a number is not in the facts (fewer decimals allowed), a report label is unknown, a medication row is not a recorded event, or a word matches the wording guardrail or causal wording ("caused", "led to", "lowered"). One retry lists the errors; a second failure answers 502 with the last saved summary, and nothing that failed is saved |
| 18 | Known limit of the number check: it is set membership, not claim checking | Every number must appear somewhere in the facts, but it is not tied to the sentence's claim. Dates put most small whole numbers (1-31) in the facts, so an invented "12%" can pass; invented decimals and computed percentages do not. The report chips and the flags page stay the source of truth |
| 19 | Gemini overload is retried in the client (2 s, then 5 s, on 429/503 only), then fallback models in order, capped at about 60 s per call | On the build day 10 of 12 calls got 503 "high demand". Waiting briefly and switching models is the right answer to overload; other errors (bad request, timeout) are not retried there, because they go to the summary's own retry, which lists what was wrong. When every model is still unavailable, the summary is not tried a second time (`LLMUnavailable`), so the doctor waits about 60 s at most before the 502; a timeout followed by the guard retry can still take about 2 minutes |
| 20 | Charts are one hand-written SVG component (`frontend/src/components/TrendChart.tsx`), not Recharts | Drug-window bands, hollow vs solid points, censored markers, the slope overlay and clickable, keyboard-focusable source points (report, lab, page, "Open report") have to match the approved design exactly; bending Recharts to do all of that is more code than drawing it |
| 21 | The UI shows numbers as the summaries do: 10 or more → one decimal; below 10 → the API's decimals (slope −7.08, creatinine 1.11) | The trends card and the summary on the same screen must not disagree (−7.1 vs 7.08) |
| 22 | UI wording for the eGFR slope rule: "Beyond the KDIGO threshold of −5 mL/min/1.73 m²/yr", never "rapid progression" | "Rapid" is on the banned-wording list; the threshold wording states the rule without a clinical label |
| 23 | The amber slope overlay is drawn only when a guideline flag fired | Amber is the only alarm colour; a dashed amber line on every analyte with a slope would read as an alert |
| 24 | Changes are shown against a guideline target ("toward" / "away from" the ADA, KDIGO or ATA goal), never as good or bad, and never in red/green | The doctor decides whether a change is good for this patient (an HbA1c of 6.4% is on target for one patient and a hypoglycaemia risk for another). Toward/away is a checkable fact with a cited source; blue/amber stays readable for red-green colour-blind viewers (about 8% of men) |
| 25 | Medication response says whether the change the catalogue expects appeared (`seen`, `not seen`, `opposite`, `above expected`), not whether the drug works | "Expected TSH fall not seen" is observed data; "levothyroxine failed" would ignore adherence, dose, timing and absorption, none of which ChronoTrace sees. Effects the source calls small (SGLT2 inhibitor and ACEi/ARB eGFR dip, potassium rise) count as seen within noise |
| 26 | A change between two labs is annotated with the change of lab, and checked against the same lab on the other side of the step | Merging reports from different labs is the product; a jump that disappears when the patient goes back to the first lab is the most common false alarm it can create. The flag is kept (the doctor decides); the note says the labs may explain it |
| 27 | Levothyroxine added to the drug catalogue (window 42–90 days, TSH fall and free T4 rise), status unverified | Needed for the hypothyroid demo patient; the ATA 2014 guideline is named but its exact wording was not checked in this session |
| 28 | Each chart point carries a noise band of ± (change threshold / √2): the spread one result can show from lab and biological variation alone | The RCV compares two results (hence √2); one result's own 95% spread is RCV/√2. It shows the doctor, on the chart, why a single step is within noise while the slope is not. For eGFR the threshold is KDIGO's 20%, so the band is a guideline-based spread rather than a measured CV |
| 29 | eGFR projection: the falling slope extended to the next KDIGO category boundary, with a 95% range from the slope's t-interval (n−2 df); shown only when the slope is "ok"; wording "a projection of past results, not a forecast" | Nephrologists already reason in slopes and categories; showing the date with its uncertainty is more honest than a single date, and a 4-point slope gets a wide t (4.3) on purpose. Nothing is projected beyond 10 years |
| 30 | Time since the last test against the interval a guideline lists (ADA section 6 and 11, KDIGO, ATA), stated as a fact with its source | "HbA1c 7 months ago · ADA: at least twice a year" is checkable; "HbA1c overdue, repeat now" would be advice, which the wording guard bans |
| 31 | Jury's "differential diagnosis / CDSS" is built as "guideline criteria met" (KDIGO CKD definition, ADA diabetes criteria, ATA thyroid patterns), each with its evidence, reports and source, for the doctor to confirm | A ranked differential from a model cannot cite why, and would contradict decision #6 (the AI never decides). A criterion is a published rule applied to confirmed values: a doctor can check it line by line |
| 32 | ICD-10 / ICD-10-CM / SNOMED CT codes come from a small offline table (`data/conditions.yaml`), not a live terminology API | The demo must not depend on a network call; the table covers the recorded conditions and the KDIGO stage codes. Production would use India's NRCeS SNOMED CT release and a terminology server. Codes are marked unverified until checked in the official browsers |
| 33 | The KDIGO grid shows the G and A categories and the patient's path only; no prognosis risk level | The team chose to show categories (measured) and leave the heat-map risk wording out of the product |
| 34 | Nutrition shows only guideline figures for the patient's computed category (KDIGO protein 0.8 g/kg/day for G3–G5, sodium < 2 g/day with CKD, ADA individualised nutrition), times the recorded weight | A per-kg figure quoted from a guideline is checkable; a meal plan would be advice ChronoTrace cannot back. Weight is optional and stored only for these figures |
| 35 | "Ask about this patient" answers only from the whole-history facts plus the clinical-support results, with report citations, through the same number, report and wording checks as the summaries; decision questions get "the decision is the doctor's"; nothing is stored | A free chat over raw reports could invent values or give advice. Grounding it in the same checked facts makes every answer traceable to R-labels, and a failed check is retried once, then shown as unavailable rather than wrong |
